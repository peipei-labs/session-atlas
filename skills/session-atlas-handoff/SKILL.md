# Session Atlas 标签、待续与收藏

为当前线程填写有助于查找的标签，并把简短交接信息或用户明确选择的参考内容交给本机 Session Atlas。待续记录已有约定的下一步；“可能有用（收藏）”只说明以后为什么值得再看，不创建新的工作目标。标签独立保存，不代表已经保存待续或收藏。

## 什么时候登记

用户只要求查找或查看卡片时，执行下面的只读查询流程，不填写当前线程标签，不登记或修改卡片，也不自动恢复线程或执行卡片里的待办。

当前采用主动登记试行：工作已经推进到必须等时间、外部条件、用户补充或用户明确要求稍后继续时，登记仍未完成的约定事项。用户也可以显式调用 `$session-atlas-handoff`。

- 仍能执行的已授权工作先继续完成，不为登记交接提前停工。
- 可选建议、未经采纳的设想、单纯的回答结束和普通关闭不产生待续事项。全部完成且没有现存卡片需要更新时，无须写入交接卡；仍可填写线程标签。
- 恢复原线程后先读取已有卡片；根据实际执行、核验或用户决定更新同一张卡。`done` 只用于已完成并达到原验收要求的事项，`cancelled` 只用于用户明确取消或替代的事项；到期不代表完成。
- 交接不关闭分屏、不发送终端输入、不代替用户按快捷键，也不安排后台执行。

收藏只在用户明确要求“收藏”“放到可能有用”或“保留供参考”时保存。普通完成、提到一个可选建议或询问“这个可能有用吗”都不自动收藏。收藏不要求未完成事项、下一步或日期，也不要为收藏编造这些字段。

## 跨卡片只读查询

用于“看看卡片里有没有关于某个主题的”“找之前的待续或收藏”等请求。`handoff.mjs read` 只能读取当前原线程，不能用于搜索全部卡片。

1. 请求本机 `GET http://127.0.0.1:4317/api/sessions`；设置了 `SESSION_ATLAS_PORT` 时使用该数字端口。使用带超时的只读请求，例如 `curl --fail --silent --show-error --max-time 15 "http://127.0.0.1:${SESSION_ATLAS_PORT:-4317}/api/sessions"`，将响应直接交给内存中的 JSON 解析器，不保存完整快照到文件或日志。
2. 确认响应是有效 JSON，且 `sessions`、`recoveries` 为数组。主要从 `recoveries` 中查找有 `handoff` 的记录，匹配 `title`、`projectName`、`tags`、`handoff.summary`、`handoff.items` 的标题/下一步/条件，以及 `handoff.reference` 的标题/原因。按用户主题补充同义词和中英文关键词；例如网络流量可用「流量、带宽、traffic、bandwidth、nettop」，不是只搜“网络流量”原词。
3. 按 `sessionId` 去重，只输出命中记录需要的字段。可用 `sessions` 补充当前会话信息；只有会话标题命中但没有 `handoff` 时，称为相关会话，不计入命中卡片。标题命中后阅读摘要和事项，确认实际相关性，不凭关键词判定。
4. 报告卡片标题、相关内容、`handoff.updatedAt` 和事项状态；时间转为 Asia/Shanghai 的绝对日期，需要区分时保留时分。提供可用于界面搜索的关键词或精确线程 ID。历史流量、费用、故障和验证结果必须标明是卡片当时的记录，不代表当前状态；`status: closed` 只表示会话关闭，不表示待续已完成。

无命中时说明“当前服务返回的卡片中未找到”，不要推断全部历史对话都没有相关内容。请求失败、超时或结构不符时说明查询未完成，不将其当作零结果，也不自动启动或重启服务。用户要求进一步排查时再核对当前服务配置和源码。查询授权不包含修改其他线程卡片或执行历史待办。

## 恢复后维护原卡

恢复后开始处理用户的下一条消息时，先用下文的 `read` 读取当前原线程的卡片。已有卡片不是新的工作授权；用户只是查看收藏时，不自动执行旧建议或未到条件的事项。

- 有待续事项：结合用户当前要求继续已授权工作。在本轮结束前，把有证据的进展、仍需等待的条件及已完成事项合并回原卡，复用事项 `id` 和本次读取的 `expectedVersion`。若本轮确实继续了已登记工作，即使仍须等待，也更新其现状，让关闭操作能核验这轮已交接；不把单纯问候或无关讨论当成进展。
- 事项确实达到原验收要求：在原卡标记 `done`，不再另建“任务完成”卡，不把其他仍未完成的事项一起结束。完成全部待续后，界面会自动移出待续列表；原有收藏继续保留。
- 只有收藏：打开、阅读和普通问答不要求重写收藏。只有用户修改保留目的，或原有主题、原因确实已被新事实取代时才更新；不能因读过一次或完成工作而取消收藏。
- 没有卡片：沿用上面的登记条件，不因为通过 Session Atlas 恢复就创建卡片。

每次实际写入后执行一次 `read`，核对本轮修改的事项状态、保留的其他事项及收藏；读回一致才告知“原卡已更新”，并简短说明还剩什么或待续已完成。冲突、超时或读取失败按下文处理；不声称已同步，也不妨碍仍可推进的原工作。无需让用户重复要求“再登记一次”。

## 线程标签

使用本 skill 时，由当前原线程根据实际工作直接填写标签，无须让用户先拟标签。通常选 2–5 个有助于区分本线程的技术、主题或任务标签，例如技术名、实际处理的业务或任务类型；不强制分类，不照抄示例，也不根据项目目录把整个项目的技术栈都贴上。只有问候、缺少具体工作内容时不编造标签。手动编辑与原线程填写共用同一组标签，其他线程或没有原线程上下文的子代理不能代写。

先读取已有标签，保留用户和其他已存在的标签；通常只用 `add` 增补本次明确缺少的标签。移除已有标签须有用户要求或原线程中可确认的纠正依据，不因自己这次选了不同标签就删除旧标签。

```bash
node ~/.codex/skills/session-atlas-handoff/scripts/handoff.mjs tags
```

读回 `{sessionId,tags}` 后，用标准输入提交增量；下面只示意字段，标签应根据当前线程填写：

```bash
node ~/.codex/skills/session-atlas-handoff/scripts/handoff.mjs tag <<'JSON'
{"add":["Python","账户核对"]}
JSON
```

`tag` 只接受 `add`、`remove` 文字数组，不接受 `sessionId`、`cwd`、`source`、`expectedVersion`，只从 `CODEX_THREAD_ID` 取当前线程身份。每个线程最多 12 个标签，每个标签经 Unicode NFKC 规范化和去除首尾空格后为 1–40 个字符；大小写重复合并，控制字符和不可见格式字符拒绝。同一个标签不能同时增删。增量提交不会替换其他已有标签，服务负责校验最终数量；超过上限时先读取已有标签，不擅自删除用户标签。

`tags` 必须返回当前身份及有效的 `tags` 数组，空输出或读取失败不能当成无标签。`tag` 在写入响应有效后会再读回一次，核对新增已存在、移除已不存在；只有退出码为 0 且明确输出“已保存线程标签”时，才报告保存成功。标签与交接卡分别报告结果，标签失败不表示卡片保存失败，也不要因此停止仍能完成的已授权工作。

标签写入超时、连接中断或结果无法确认时，保持“标签保存结果未确认”，不能断言没有保存。允许执行一次 `tags` 只读核对本次增删；一致时说明已读回确认，否则不盲目重复 `tag`。单独填写标签不调用卡片 `write`，不创建待续或收藏，也不关闭分屏。

## 交接卡读取和写入

在当前项目工作目录执行。安装后的脚本位置为 `~/.codex/skills/session-atlas-handoff/scripts/handoff.mjs`；开发时可使用此 skill 目录内的脚本。

```bash
node ~/.codex/skills/session-atlas-handoff/scripts/handoff.mjs read
```

脚本只从当前进程的 `CODEX_THREAD_ID` 取得线程身份。服务核验原线程记录后，使用记录中的工作目录保存卡片；脚本可以在该线程正在使用的 worktree 或子目录运行，不需要切回最初启动目录，也不要手填 `cwd`。缺少或无法验证身份时停止登记并说明原因，不猜测 session ID、不使用 `--last`、不为其他线程写入，不手动伪造环境变量绕过检查。

每次修改前先读取现有卡片。保留现有事项的 `id`、用户修改、收藏和仍有效的其他事项，将这次有证据的变化合并后一次写入；不要用这轮对话的局部信息覆盖整张旧卡。当前用户的新要求或已验证的新事实取代旧内容时，只更新被取代的部分。输入 JSON 只经标准输入传递，不写临时交接文件或命令行参数。只提交下述输入字段，读取结果中的 `sessionId`、`source`、`updatedAt`、`version` 不原样回传。

`read` 同时返回 `expectedVersion`：已有卡片取 `version`，旧卡片取 `updatedAt`，没有卡片时为 `null`。写入和移除必须提交用于组织本次内容的那次读取所返回的 `expectedVersion` 原值。不能给旧内容补上新读取的版本后直接提交；需要重新合并最新卡片和本次意图。以下首次登记示例只适用于读取确认没有卡片的情况；更新已有卡片时将 `null` 换成该次读取的版本字符串。

```bash
node ~/.codex/skills/session-atlas-handoff/scripts/handoff.mjs write <<'JSON'
{
  "expectedVersion": null,
  "summary": "保留本次工作的用途、目前已做到哪里，以及恢复时需要的短说明。",
  "items": [
    {
      "id": "verify-after-observation",
      "title": "观察期结束后核验结果",
      "kind": "time",
      "nextAction": "按已约定的验收标准检查结果并更新本项状态。",
      "status": "pending",
      "anchorLabel": "实际观察开始时间尚未确认",
      "delayHours": 24
    }
  ]
}
JSON
```

示例仅说明字段；不要照抄示例内容作为真实待办。写入成功只输出 session ID、事项数量和是否有收藏。只有退出码为 0 且脚本明确输出“已保存待续卡”或“已保存会话卡”时，才能按写入结果报告成功；退出 0 但输出为空不代表保存成功，应按结果未确认处理。`read` 必须返回包含当前 `sessionId`、`handoff`、`expectedVersion` 的 JSON，供合并和继续使用；空输出不等于没有卡片，不要据此使用 `expectedVersion: null`。读取内容不要转存到日志或其他系统。

写入成功后，若原线程的 iTerm 分屏当前在线且身份可唯一核验，服务会把该分屏的 Tab 标为紫色并追加“Atlas · 已保留”副标题，作为已登记的可见标记。分屏不在线、身份不唯一或标记失败都不影响登记结果，也无须为此重试写入；之后通过 Session Atlas 打开或回到该线程时会重新核验并补打标记。

## 事项和时间

一张卡最多 20 项。`summary` 最多 1000 字符；每项必填 `id`（最多 100 字符）、`title`（最多 200 字符）、`kind`、`nextAction`（最多 1000 字符）、`status`。新增项使用简短稳定标识，如 `verify-next-day`；后续更新复用它。

| kind | 适用情况 | 需要说明 |
| --- | --- | --- |
| `time` | 约定某时或经过一段观察期再核验 | 实际起算事件和有依据的时间 |
| `condition` | 等外部条件成立 | `condition` 写明条件，最多 1000 字符 |
| `input` | 等用户补充信息或要求 | `condition` 写明缺少什么，最多 1000 字符 |
| `later` | 用户明确要求稍后继续 | `nextAction` 写明恢复后的第一步 |

时间可填 `anchorLabel`、`anchorAt`、`delayHours`、`dueAt`。绝对时间必须带时区，例如 `2026-09-09T18:00:00+08:00`；根据原会话的真实事件填写。相对等待提交已知的 `anchorAt` 和 `delayHours`，由服务计算到期时间。缺少时间证据时保留说明和时长，省略 `anchorAt`、`dueAt`，界面会显示时间待确认。不能把当前时间、登记时间或关闭时间当作原约定的起算点。

`status` 只能为 `pending`、`done`、`cancelled`。更新完成或取消状态时仍保留其他事项；卡中不再有待办后会退出待续列表，已有收藏继续保留。可选字段 `sourceTurnId` 只填写当前运行环境已知的真实 turn ID。`requiresRunningProcess: true` 只用于约定必须让当前进程继续运行的情况，此时快捷键会保留分屏，直到该要求确实解除。

## 可能有用（收藏）

收藏使用可选字段 `reference`，包含非空 `title`（最多 200 字符）和 `reason`（最多 1000 字符）。写清原线程讲什么，以及用户为什么希望以后再看；不复制完整对话。

读取确认没有已有卡片时，只收藏可提交下面的结构，`summary` 可与收藏标题相同，`items` 仍必须提交空数组：

```json
{
  "expectedVersion": null,
  "summary": "本次讨论的参考标题",
  "items": [],
  "reference": {
    "title": "本次讨论的参考标题",
    "reason": "用户希望以后重新查看的具体原因。"
  }
}
```

- 已有待续事项时，保留读取到的 `summary`、完整 `items` 和 `requiresRunningProcess` 等仍有效的输入字段，只新增或更新 `reference`；不能为了收藏把 `items` 置空。
- 只更新待续事项时省略 `reference`，服务会保留已有收藏；完成全部待续也不取消收藏。
- 用户仅要求取消收藏时，保留原 `summary`、完整 `items` 和其他仍有效的输入字段，再提交 `reference: null`。省略 `reference` 与传入 `null` 的含义不同。
- 只有用户明确要求移除包含待续和收藏的整张卡时，才先读取卡片，再执行以下命令，将示例字符串替换为该次读取的 `expectedVersion` 原值。单独取消收藏、完成或取消待续事项都使用 `write`。

```bash
node ~/.codex/skills/session-atlas-handoff/scripts/handoff.mjs remove <<'JSON'
{"expectedVersion":"本次读取返回的版本字符串"}
JSON
```

## 内容和失败处理

只保存恢复工作或日后查阅必需的短说明，不复制完整对话、提示词、终端输出、凭证或审批载荷。内容只发往 `127.0.0.1`，默认端口 `4317`；本机服务使用其他端口时可设置数字型 `SESSION_ATLAS_PORT`。

以下失败处理针对交接卡；标签按上面的独立流程处理。输入校验未通过、请求尚未发出，或服务明确拒绝写入时，说明“本次交接未保存”和脚本给出的简短原因；这不代表之前保存的卡片不存在。

脚本只解释已知错误码，不输出服务响应中的原始 `message` 或正文。按具体原因处理：

| 错误码 | 本次结果与下一步 |
| --- | --- |
| `SESSION_CWD_MISMATCH` | 目录校验拒绝保存。检查服务是否已更新；不要伪造线程身份或手填目录绕过。 |
| `SESSION_RECORD_UNAVAILABLE` / `SESSION_RECORD_INVALID` | 原线程记录无法唯一核验或解析，未保存。检查记录的可读取性和有效性。 |
| `SESSION_IDENTITY_MISMATCH` | 当前身份不是可核验的原线程，未保存。回到原线程执行，不替其他线程或子代理登记。 |
| `HANDOFF_BUSY` | 同一线程的其他操作尚未结束，未保存。操作结束后先读取卡片，再合并本次变化。 |
| `HANDOFF_CONFLICT` | 卡片已被更新或移除，未保存。重新读取并合并最新卡片与本次意图；不能只替换 `expectedVersion` 或重试旧内容。 |
| `HANDOFF_VERSION_REQUIRED` | 缺少有效版本，未保存。提交组织本次内容时读取的 `expectedVersion`，没有卡片时才用 `null`。 |

如果工具提示 `failed to spawn code-mode host`、找不到宿主程序等启动失败，脚本尚未执行，交接请求也尚未发出，应明确说明“本次交接尚未执行”。先排查工具运行环境；不能改填其他线程身份绕过，也不能把宿主启动失败说成 Session Atlas 已拒绝保存。

写入请求超时、连接中断或返回结果无法确认时，只能说明“本次保存结果未确认”，不能断言没有保存。保持同一线程身份，允许执行一次 `read` 只读核对：读回的事项、状态、时间依据及本次涉及的收藏变化一致时，说明已读回并确认；未找到、不一致或读取也失败时，保留“结果未确认”，不盲目重复写入。脚本本身不自动重试。

保持原工作结果，不关闭分屏、不反复请求、不另建文件或改写全局配置。成功后简短告知已登记的下一步或已收藏供参考，不把保存成功说成工作已经完成。
